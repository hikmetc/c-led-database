# EFLM Laboratory Error Database - structure and maintenance

This document describes how the database is laid out, what every file and column means, what rules the data must satisfy, and exactly how to extend it. It is generated by `scripts/mk_structure_doc.py` from the live data, so its counts never drift.

State at generation: **8 analytes**, **136 interference causes**, **117 evidence tables**, **11,918 evidence rows**, **783 distinct references**.

---

## 1. What this database is

One row of the database is one piece of published evidence that a named interferent changed the measurement of a named analyte, recorded with the direction and size of the error, the measurement platform it was observed on, an appraisal of the study, and a citation.

Each analyte carries one **analytical performance specification (APS)**: a relative allowable bias. Every row is judged against it. The APS is data, not prose, so a website can show it and can re-judge every row against a user-supplied APS instead.

The scope is **analytical interference and pre-analytical error**: things that make the measured value differ from the true value. It is not a database of reference intervals, clinical decision limits or drug effects on physiology.

## 2. Design principles

1. **The CSVs are the source of truth, and the build never writes to them.** Everything in `meta/` and `build/` is regenerated from scratch by `scripts/build_all.py`.
2. **The source text is kept verbatim.** Wording, spelling and units are preserved exactly as each paper printed them. Normalisation is added alongside as derived fields, never by overwriting the original.
3. **The vocabulary lives in one file.** `scripts/registry.py` holds every analyte, every canonical interferent and every table mapping. Nothing else defines them.
4. **Generated data is never committed.** `build/` is rebuilt by CI; committing it would add a fresh multi-megabyte blob to git history on every rebuild and would eventually exceed GitHub's 100 MB per-file limit.
5. **The website reads Parquet and only Parquet.** The web layer is columnar, compressed and cut per analyte, so it stays small and fast as the database grows.
6. **No identifier is ever invented.** A DOI or PubMed ID is written only when it was read from the source or resolved against PubMed or Crossref, and then with its provenance recorded in `meta/references_enriched.csv`.
7. **A row with no data is not evidence.** See section 9.

## 5. The evidence table

Every table in every `database/` folder has the same 29 columns, in the same order. `scripts/validate.py` fails the build if any table differs, or if the data dictionary and the real header fall out of step.

A table is normally one interferent. Where a table genuinely covers several distinct agents (a cardiac-glycoside panel, a group of factor Xa inhibitors), the rows are split by wording rules instead: see section 10.

| # | Column | Parquet column | Type | Values | Meaning |
|---|---|---|---|---|---|
| 1 | Analyte | `analyte_verbatim` | string | verbatim | Analyte (measurand) exactly as named in the source publication. Spelling varies between papers; use analyte_id / component from analytes.csv for filtering. |
| 2 | Interferent | `interferent_verbatim` | string | verbatim | Interfering substance or condition exactly as named in the source publication. Use interferent_id (see interferent_synonyms.csv) for filtering. |
| 3 | Platform/Brand/Method | `platform_brand_method` | string | verbatim | Measurement principle, assay brand or method as reported (e.g. CO-oximetry, FPIA, immunoturbidimetry). |
| 4 | Analyzer/Instrument | `analyzer_instrument` | string | verbatim | Analyser or instrument on which the measurement was made. |
| 5 | Assay generation/version | `assay_generation_version` | string | verbatim | Assay generation, kit version or lot where the source reports it. |
| 6 | Direction of effect | `direction_of_effect` | enum | up / down / no change / not reported | Direction of the measurement error caused by the interferent, as reported: up = falsely increased, down = falsely decreased, no change = no detectable effect. |
| 7 | Direction (study criterion) | `direction_study_criterion` | enum | up / down / no change / not reported | Direction judged against the criterion used by the source study itself. |
| 8 | Direction (user APS) | `direction_user_aps` | enum | up / down / no change / not reported | Direction judged against the analytical performance specification selected for this database (aps_percent). |
| 9 | Interferent concentration (exact, with units) | `interferent_concentration_exact_with_units` | string | verbatim, units embedded | Concentration or dose of the interferent, with the units used by the source. Free text: not directly plottable. |
| 10 | Baseline analyte concentration | `baseline_analyte_concentration` | string | verbatim, units embedded | Analyte concentration before or without the interferent, with source units. Free text. |
| 11 | Final analyte concentration | `final_analyte_concentration` | string | verbatim, units embedded | Analyte concentration in the presence of the interferent, with source units. Free text. |
| 12 | Absolute change (as reported) | `absolute_change_as_reported` | string | verbatim, units embedded | Absolute change printed by the source, in the source's units. |
| 13 | Percentage change (as reported) | `percentage_change_as_reported` | string | number or text | Relative change printed by the source, in percent. |
| 14 | Absolute change (calculated) | `absolute_change_calculated` | string | number or text | Absolute change derived from the baseline and final values in the source. |
| 15 | Percentage change (calculated) | `percentage_change_calculated` | number | percent | Relative change in percent derived from the baseline and final values. This is the primary machine-readable effect size (pct_change in the derived build). |
| 16 | Magnitude of change (verbatim from source) | `magnitude_of_change_verbatim_from_source` | string | verbatim | The source's own wording for the size of the effect. |
| 17 | Significant-bias threshold | `significant_bias_threshold` | string | verbatim | The threshold the SOURCE STUDY used to call a bias significant (often a statistical test, sometimes a percentage, often not reported). Not the database APS. |
| 18 | Clinical significance vs user APS | `clinical_significance_vs_user_aps` | string | verbatim, contains the verdict | Whether the observed effect exceeds the analytical performance specification selected for this database. The verdict is parsed into aps_verdict in the derived build. |
| 19 | Sample type | `sample_type` | string | verbatim | Specimen used (whole blood, serum, plasma, pooled plasma, postmortem blood, body cavity fluid and so on). |
| 20 | Study method details | `study_method_details` | string | verbatim | How the interference was produced and measured: spiking, in vivo exposure, patient samples, comparison arms. |
| 21 | Physiologically realistic concentration? | `physiologically_realistic_concentration` | enum | Yes / Partial / Borderline / Unclear / not reported | Appraisal: whether the interferent concentration tested can occur in patients. |
| 22 | Study design appropriate? | `study_design_appropriate` | enum | Appropriate / Partially appropriate / Inappropriate / Unclear / not reported | Appraisal of the study design for an interference claim. |
| 23 | Clinically significant effect? | `clinically_significant_effect` | enum | Yes / No / Partial / Unclear / not reported | Appraisal of whether the effect matters clinically. |
| 24 | Real-world conditions reflected? | `real_world_conditions_reflected` | enum | Yes / No / Partial / Unclear / not reported | Appraisal of how well the experiment reflects routine practice. |
| 25 | Additional sources of bias | `additional_sources_of_bias` | string | verbatim | Other biases the source reports or that are evident in it. |
| 26 | Notes | `notes` | string | verbatim | Free-text notes recorded during extraction. |
| 27 | Citation | `citation` | string | verbatim | Short citation plus the exact locator inside the source (page, table, figure). Often names the source PDF file. |
| 28 | Full reference (from PDF) | `full_reference_from_pdf` | string | verbatim | Full bibliographic reference as printed in the source document. |
| 29 | doi | `doi_as_printed` | string | DOI or 'not reported in the information source' | Digital Object Identifier of the source publication. |

### Reading the columns correctly

- **`Significant-bias threshold` is the source study's own criterion**, not the database APS. It is often a statistical test and frequently not reported. The database APS lives in `meta/analytes.csv`. Never conflate the two.
- **`Percentage change (calculated)` is the primary effect size.** It is derived from the baseline and final values printed in the source. `Percentage change (as reported)` is what the paper printed itself, which is often absent.
- **The concentration and change columns carry their units inside the text**, because sources report in incompatible units. They are not directly plottable.
- **`not reported in the information source` means the source does not state it.** It never means zero, and must never be plotted as zero.

### Why the synonym table exists

The same cause is worded differently by nearly every paper. Across the database there are **1,133 distinct interferent wordings** for **136 causes**: hemolysis alone appears as "Hemolysis (hemolysis index HI)", "Haemolysis, free haemoglobin", "Hemolysis / hemoglobin (hemolysate)" and many more. Filtering on the verbatim text therefore finds almost nothing. `interferent_synonyms.csv` maps every wording to one `interferent_id`, and the derived build carries that id on every row. **Facet filters must use `interferent_id` or `concept`, never the verbatim text.**

### Identifier scheme

| Identifier | Form | Example | Stability |
|---|---|---|---|
| `analyte_id` | short prefix | `cohb` | permanent; must be unique |
| `interferent_id` | `<analyte_id>.<key>` | `cohb.ascitic_fluid` | permanent once published |
| `row_id` | `<analyte_id>.<table stem>.<row number>` | `cohb.carboxyhemoglobin_blood-ph_20261026-1304_APS1_extraction_table.0002` | stable while rows are appended, not if rows are inserted mid-table |
| `concept` | shared vocabulary | `hemolysis` | shared across analytes |


| Step | Script | Reads | Writes |
|---|---|---|---|
| 1 | `build_vocab.py` | `registry.py`, evidence tables | `meta/interferents.csv`, `meta/interferent_synonyms.csv`, `meta/table_index.csv` |
| 2 | `build_meta.py` | registry, evidence tables, interferents | `meta/analytes.*`, `meta/data_dictionary.*`, `meta/file_index.csv`, per-analyte analyte and interferent-list CSVs |

## 8. `build/` - the derived layer

`build/` has two parts with very different jobs. Only the first is ever published.

### 8.1 The Parquet web layer - what the website reads

```
build/parquet/
|-- manifest.json                 schema version, every file, row counts, byte sizes, columns
|-- slim_all.parquet              every row, slim columns, sorted by analyte_id, interferent_id
|-- slim/<analyte_id>.parquet     slim columns for one analyte, sorted by interferent_id
`-- detail/<analyte_id>.parquet   row_id + every source column, sorted by row_id
```

Why Parquet: the evidence text is highly repetitive (the same citations, platforms and 'not reported' phrases recur thousands of times), so a columnar, dictionary-encoded, zstd-compressed file is 20-40 times smaller than the same rows as JSON. And because Parquet stores per-row-group statistics and a footer index, DuckDB-WASM in the browser reads only the columns and row groups a query needs, over HTTP range requests.

How the files are cut, and why:

| File | Sorted by | Row group | Read by |
|---|---|---|---|
| `slim_all.parquet` | `analyte_id`, `interferent_id`, `row_id` | 8,192 rows | overview, search, cross-analyte (concept) views; analyte filters skip whole row groups |
| `slim/<id>.parquet` | `interferent_id`, `row_id` | 10,000 rows | an analyte page: table, facets, charts, custom APS |
| `detail/<id>.parquet` | `row_id` | 2,000 rows | the row drawer and row permalinks; one row reads one row group, not the file |

Current layer: schema `1.0`, 11,918 rows, compression `zstd-19`; `slim_all.parquet` 0.27 MB.

## 9. What counts as evidence

**Rule: a row with no value in any of the 11 data fields is not evidence.** The eleven are direction of effect, the four change columns, magnitude, baseline and final concentration, interferent concentration, platform and analyzer.

Such rows arise when the cited document could not supply anything: a scan with no text layer, a journal masthead downloaded instead of the article, a publisher permissions sheet, or a paper that turns out to be about a different analyte. `scripts/prune_unevidenced_rows.py` applies the rule, archives every removed row with its full columns and the reason in `meta/removed_rows.csv`, and deletes a table that ends up empty.

Run it after importing a new analyte, then re-register, then rebuild.

## 10. Tables that cover several causes

Most tables are one cause, declared in `TABLE_MAP`. Where one table genuinely covers several agents, add wording rules to `OVERRIDES`:

```python
OVERRIDES["inr_plasma"]["inr_fxa_interference_extraction.csv"] = [
    (r"rivaroxaban", "rivaroxaban"),
    (r"apixaban",    "apixaban"),
    (r"edoxaban",    "edoxaban"),
]
```

Each rule is a regular expression matched case-insensitively against the row's verbatim interferent text, in order; the first match wins, and a row that matches nothing falls back to the table's default id. Keep the default id in `CANON` as the catch-all even when no row currently uses it.

## 11. References

Every row must identify its source. `reference_status` records how:

| Status | Rows | Meaning |
|---|---|---|
| `doi` | 6,177 | DOI present |
| `pmid` | 1,195 | no DOI, PubMed ID present |
| `reference_only` | 4,546 | no DOI or PubMed ID, full bibliographic reference present |
| `citation_only` | 0 | author and year only |
| `unidentified` | 0 | none of the above; listed in `meta/known_gaps.csv` |

7,372 of 11,918 rows carry a DOI or a PubMed ID.

When an identifier is missing from the source table but can be established - from the PDF title page, from PubMed or Crossref, or from a publisher article identifier encoded in a file name - it goes in `meta/references_enriched.csv`, keyed by the source PDF, with the method used and what it was checked against. The build fills it in and marks the row `reference_origin = enriched`. **The source tables are never edited to add it.** An identifier that cannot be established is left alone; nothing is guessed.

## 12. Full-text PDFs

Publisher full texts are **not distributed**: they are under copyright. They live in the local working copy under `<analyte>/fulltext_pdfs/<interferent>/`, one folder per interferent, and `.gitignore` keeps them out of git. Every row carries a DOI, a PubMed ID or a full reference instead, so the source can always be retrieved at its publisher.

## 13. Invariants the build enforces

`scripts/validate.py` fails the build on any of these:

- an analyte folder holds evidence tables but is not registered, or a registered analyte has no folder
- an evidence table exists on disk but is not in `TABLE_MAP`, or vice versa
- the registry is internally inconsistent: duplicate prefixes, a table pointing at an unknown interferent key, an override that is not a list of `(regex, key)` pairs
- the evidence tables do not all share one identical header, or the header and the data dictionary disagree
- a row reaches no canonical interferent
- a `row_id` is missing or not unique
- the row count in the build does not match the row count in the CSVs
- a file name is not portable, or a PDF sits anywhere it would be committed
- an evidence CSV exceeds 90 MiB (GitHub rejects files over 100 MiB; split the table)
- the Parquet layer is stale or inconsistent: its row count differs from the evidence, the slim, detail and slim_all counts disagree, a listed file is missing, there is not exactly one slim file per analyte, or `row_id` repeats in `slim_all.parquet`
- the web deploy set exceeds 900 MB
- `CLED_REQUIRE_PARQUET=1` is set (as in CI) and the Parquet layer is missing

It warns, without failing, on a UTF-8 BOM, an over-long path, an evidence CSV over 50 MiB, a deploy set over 500 MB, and rows listed in `meta/known_gaps.csv`.

## 14. Adding an analyte

1. **Create the folder and drop in the tables.**

   ```
   <new_analyte>/database/<table>.csv
   ```

   Every table must carry the same 29 columns in the same order. Copy the header from any existing table. Use one table per interferent where you can.

2. **Remove rows that carry no evidence.**

   ```bash
   python3 scripts/prune_unevidenced_rows.py .
   ```

3. **Register it** in `scripts/registry.py`, in three places:

   ```python
   ANALYTES["magnesium_serum"] = dict(
       prefix="mg", component="Magnesium", system="Serum",
       kind_of_property="Substance concentration", unit="mmol/L",
       aps_percent=1.8, aps_note="",
       synonyms="Magnesium; Mg; total magnesium")

   CANON["magnesium_serum"] = {
       "hemolysis": ("Hemolysis / free haemoglobin", "hemolysis"),
       "lipemia":   ("Lipemia (triglycerides)", "lipemia"),
   }

   TABLE_MAP["magnesium_serum"] = {
       "magnesium_hemolysis_interference.csv": "hemolysis",
       "magnesium_lipemia_interference.csv":   "lipemia",
   }
   ```

   Give the analyte a `prefix` no other analyte uses. Reuse an existing `concept` string wherever the cause already exists for another analyte - that is what makes the cross-analyte view work. Add `OVERRIDES` only for a table that covers several distinct agents.

4. **Build.**

   ```bash
   pip install -r requirements.txt   # once
   python3 scripts/build_all.py
   ```

   Nothing else is written by hand. The analyte record, the interferent list, the analyte's markdown page, the registries, the README table, this document, the internal SQLite and the **Parquet web layer** - its own `slim/<id>.parquet` and `detail/<id>.parquet`, a new entry in `manifest.json`, and its rows in `slim_all.parquet` - are all generated. The website picks the new analyte up from `manifest.json` and `analytes.json` with no code change. If anything is missing or inconsistent, the build stops and names it.

5. **Audit.**

   ```bash
   python3 scripts/audit_evidence.py .
   ```

   Expect zero rows without a citation, zero rows with no value in any data field, and zero rows citing a document that supplied nothing.

### Importing a run of the literature archive

`scripts/import_archive.py <path>` performs steps 1 to 5 for one extraction run of the literature archive. `<path>` is a run folder, a topic folder (its latest run is used) or an extraction table. The importer:

- picks the highest `_vN` version of the run's extraction table and stores it under one stable name, `<run id>_extraction_table.csv`, so a newer version of a run replaces the older one instead of adding the same evidence twice, and the run's `row_id`s keep their table stem
- refuses a table whose header is not the 29 columns of section 5
- matches the analyte against the registry (folder, prefix, component, synonyms); for an analyte that is not registered it asks for prefix, component, system, kind of property and unit, and takes the APS from the run
- files the table under an existing canonical cause when the key matches, and otherwise asks for a canonical name and a concept; it never invents either
- warns and stops when the cause already has another table, because the same studies would then be counted twice (`--allow-duplicate-cause` overrides this for tables that hold different studies)
- edits `scripts/registry.py`, verifies that the edited registry is exactly the old one plus the planned entries, prunes rows without evidence, rebuilds, validates and audits
- undoes every change if any of that fails, which is why it requires a clean working tree
- shows what changed and asks before it commits and pushes; the push triggers the data and website workflows, so the evidence is on the website a few minutes later

Only the extraction CSV is copied. The archive is read, never changed. `--dry-run` shows the plan and changes nothing; `--no-push` imports and rebuilds without committing.

### Inclusion screening

`scripts/screening.py` decides, row by row, whether a row may enter the database, and says why not. The importer applies it with `--screen`; the manager app applies it before every import and on demand for any table. Nothing is rejected without confirmation, and every rejected row is archived in full in `meta/rejected_rows.csv` with its criteria, the reason, the date and whether it was decided automatically or by hand.

| # | Criterion | Decided |
|---|---|---|
| 1 | Not enough information to find the source: no DOI, no PubMed ID, no full reference, and a citation without an author and a year | automatically |
| 2 | No citation | automatically |
| 3 | No value in any of the 11 data fields | automatically |
| 4 | The source did not measure this analyte | by hand |
| 5 | The cited file is not the article | by hand |
| 6 | The table does not have the 29 columns | at import (whole table) |
| 7 | A row reaches no canonical interference cause | by the build |
| 8 | Duplicate of another row: same source, platform, analyzer, concentrations and values | automatically |
| 9 | The DOI is malformed, or doi.org does not know it (optional online check) | automatically |
| 10 | Out of scope: not analytical interference or pre-analytical error | by hand |
| 17 | The recorded APS verdict contradicts the numeric change (a change exactly equal to the APS is not a contradiction) | automatically |

The numbers are those of the criteria list the maintainer works from; 11 to 16 and 18 to 20 are flags, not rejections, and are not applied. Criteria 4, 5 and 10 cannot be decided from a row alone: the screening only points at rows worth reading (an analyte wording that matches none of the analyte's names; text that mentions a problem with the source file). Criterion 17 compares the verdict written during extraction with `abs(percent change) > APS`; where an analyte's APS is read as an absolute difference in some sources (see its `aps_note`), a flagged row can be right and is kept by unticking it.

### The manager app

`manager/` is a desktop app (macOS) over the same process. It reads three places - this repository folder, `origin/main` on GitHub and the deployed website - and shows where they differ. It imports archive runs through `scripts/import_archive.py`, and it can change values, delete rows, add a row and delete a table. Each of these is a transaction: a plan is shown, you confirm, the files are edited, the build, the validation and the audit run, and the result is committed locally; on any failure every file is restored. Publishing (the push) is a separate confirmed step. Deleting rows renumbers the rows after them, which the plan states. It can also edit an analyte's name, system, unit, kind of property, APS and synonyms, delete an analyte, and rename a cause or move it to another concept; it edits `scripts/registry.py` for these and verifies that the edited registry is exactly the old one plus the planned change. Folder names, id prefixes and cause keys cannot be changed. See `manager/README.md`.

### Adding a table to an existing analyte

Drop the CSV into that analyte's `database/`, add one line to its `TABLE_MAP` entry, add the cause to `CANON` if it is new, and rebuild. Appending rows to an existing table needs no registry change at all.

## 15. Using the data in a website

- **Publish only the deploy set** (section 8.2). Never publish `cled.sqlite` or the legacy JSON.
- **Engine.** Any Parquet reader. This site uses hyparquet, a small JavaScript reader, and filters and aggregates in memory: DuckDB-WASM is a download of about 8 MB before the first query, which delayed the first chart by a minute or more on a slow connection. DuckDB-WASM remains a good choice for ad-hoc SQL over the same files.
- **Never hard-code analytes.** Read `parquet/manifest.json` and `analytes.json` at start-up; every analyte, file and row count is listed there.
- **Which file for which view.** Home and cross-analyte views: `slim_all.parquet`. Analyte page: `slim/<id>.parquet`. Row drawer and permalink `/row/<row_id>`: `detail/<id>.parquet WHERE row_id = ...` - the analyte id is the part of `row_id` before the first dot.
- **Filter** on `analyte_id`, `interferent_id`, `concept`, `direction`, `aps_verdict` and the four appraisal fields - never on verbatim text.
- **Search** the short text columns of `slim_all.parquet` (`interferent_canonical`, `interferent_verbatim`, `platform`, `analyzer`, `sample_type`); search long verbatim text in `detail/` only within the analyte in view.
- **Custom APS.** Every row carries `pct_change` and the analyte's `aps_percent`, with `exceeds_aps` precomputed for the database APS. For a user-supplied APS, recompute `abs(pct_change) > user_aps` in the browser. Where `pct_change` is null, fall back to the `aps_verdict` string and show it as a judgement that cannot be recomputed.
- **Charts.** Only 6,601 of 11,918 rows (55%) carry a numeric effect size. Draw from the `plottable` subset and present the rest as an evidence list; never read a missing value as zero and never let a missing value break the page. Effect sizes span orders of magnitude, so use a scale that keeps both small and extreme values readable.
- **Fallback.** Range requests can fail in some browsers, in which case the whole file is downloaded. Because files are cut per analyte, that fallback stays small and the page still works.

## 16. The website

The website lives in `site/` (SvelteKit 2, Svelte 5, TypeScript, static adapter) and is deployed to GitHub Pages by `.github/workflows/pages.yml`: data build, unit tests, site build, size and budget checks, end-to-end tests, deploy. Nothing generated is committed.

### Page map

| Route | What it shows | Data it reads |
|---|---|---|
| `/` | search, key numbers, the concept x analyte matrix, analyte cards | registry JSON; `slim_all.parquet` for the matrix shares |
| `/analyte/<analyte_id>/` | APS control, filters, ranked interferents, effect strip, direction breakdown, evidence table, CSV download | `slim/<id>.parquet` |
| `/interferent/<interferent_id>/` | the same blocks for one cause of one analyte | `slim/<id>.parquet` |
| `/concept/<concept>/` | one concept across analytes, one strip per analyte on a shared axis | `slim_all.parquet` |
| `/search/?q=` | analytes, concepts, interferents and matching evidence rows | registry JSON; `slim_all.parquet`; `detail/*.parquet` only when citations are included |
| `/row/<row_id>/` | every source column of one row, verbatim; also shown as a drawer elsewhere | `detail/<id>.parquet`, `slim/<id>.parquet` |
| `/about/` `/methods/` `/data-dictionary/` `/cite/` `/changelog/` `/downloads/` | documentation | registry JSON, `data_dictionary.json`, `CHANGELOG.md` |

Every page that can be known at build time is prerendered from `manifest.json` and the registry JSON. Row permalinks are rendered in the browser through the static fallback page (`404.html`).

### Data contract

- The site reads only the web deploy set (section 8.2), copied into `site/static/data/` at build time by `site/scripts/copy-data.mjs`, plus `meta/data_dictionary.json` for column definitions. `site/scripts/check-budget.mjs` fails the deployment if anything else appears under `data/`.
- `parquet/manifest.json` decides which analytes exist and which file each view reads. Its `schema_version` is checked: a major version the site does not know produces an error banner instead of data.
- Nulls stay nulls. A missing `pct_change` is shown as "Not reported", is never drawn and never counted as zero. Charts draw only `plottable` rows and state how many rows were left out.
- Custom APS: `exceeds = abs(pct_change) > APS`, strictly, and only where `pct_change` is numeric. Other rows keep their recorded `aps_verdict` and are marked not computable. The override is kept in the URL (`?aps=5`).
- Effect sizes span several orders of magnitude, so the default x scale is symmetric log. The alternative linear scale is clipped at a data-driven bound; values beyond it are drawn at the edge with their own marker and counted in a note, never dropped.
- Source columns are shown verbatim in the row view, under their data-dictionary names.
- Reading: `site/src/lib/data/store.ts` reads Parquet with hyparquet (zstd through fzstd). A file under 4 MB is fetched whole in one request and decoded once; a larger file is read over HTTP range requests (footer, then the needed columns and row groups; a single row of a detail file is found through the `row_id` statistics of its row groups). If a range read fails, the whole file is fetched. Decoded tables stay in memory, so filters, sorting, the APS control and the charts never wait for the network again.
- Each page preloads its own data file with the HTML, so the download starts before any script runs. The site makes no third-party request.

### How a new analyte appears

Nothing in `site/` names an analyte, an interferent or a file. After section 14, commit and push: the Pages workflow rebuilds the data, and the new analyte is in the navigation, the home cards, the matrix and the sitemap, with its own prerendered pages. `site/tests/e2e/growth.spec.ts` guards this: it builds the unchanged site against a copy of the data that holds one extra, fake analyte (`site/tests/fixtures/make_growth_data.py`) and checks that it appears everywhere. The fixture exists only in that test build and is never published.

## 17. Known limitations

- `pct_change` is present for 6,601 of 11,918 rows. Many sources report an effect only in words or only in absolute units.
- Concentration and change columns keep their units inside the text and are not directly comparable across sources.
- `aps_verdict` is parsed from prose written during extraction, so `other` and `not_computable` both occur.
- `row_id` shifts if rows are inserted in the middle of a table rather than appended.
- Some interferent names in the sources carry a non-English gloss in brackets, kept verbatim. All canonical names, concepts and documentation are English.
